## 2. G04 已验收接口与故障边界

完整输入、采集、检查点和导出契约以 README 与源码为准，不复制或重写核心实现。

- integrations.github.tasks:registry 只注册 github.refresh，模型 RefreshInput，默认策略为
  2 次额外重试、5/60 秒退避、300 秒单次超时。任务返回 None，从执行上下文读取 Job/Attempt。
- tasks.execute_refresh(data, ExecutionIdentity, *, credential=None, transport=None, trust_env=True)
  复用 collect_project/collect_issues。False 表示完整输入已完成并重建导出，重试不再次采集。
  project.refresh_project/issues.refresh_issues 的原独立入口仍可用；它们本身不生成正式文件。
- python -m integrations.github 提供 init/submit/reconcile/show/export/direct。
  默认状态目录 .taskforge/github，tasks.sqlite 与 business.sqlite 独立。
  init/submit/direct 支持 --config；submit/direct 支持 --source/--refresh-id/--rebaseline。
  省略 source 处理全部来源；省略 refresh-id 是新刷新，相同显式 UUID 才是重复意图。
- BusinessStore.prepare_intent 将新代次与意图同事务保存，已有完整输入不推进代次。
  submit 无凭据时在意图及核心 Job 前失败；意图后只调用一次公开 TaskForge.submit。
  不确定提交按公开 Job ID get，关联中断按 refresh_id 分页 list，并核对任务名与全部输入。
  查询失败、零匹配、重复匹配或输入冲突不允许再次 submit；零匹配仍待核对。
  reconcile --job-id 必须配 --refresh-id，且不能覆盖已有不同关联。
- show 只组合业务公开读取和核心 get/history；未知来源/意图报错，FAILED 状态明确。
  direct 用独立 direct-UUID 复用同一业务边界，拒绝已有核心 Job 关联的意图。
  正常退出码 0，失败/待核对 1，Typer 输入错误 2。不同来源的业务失败相互隔离。
- receipts/<refresh_id>.json、indexes/<source_id>.md 从数据库重建；逐文件临时写入/fsync/
  原子替换，导出失败保留业务 commit，可重试或 export 修复。来源锁持续到真实资源/线程清理结束。
  索引和多个收据不是一笔文件事务；对应 SIGKILL 遗留临时文件在下次持锁写入时清理。
- 批次 coverage 保存采集时相对源码/聚合 SHA-256、Git HEAD（可空）、UTC、配置/检查点及请求计数。
  batch_counts 是批次载荷计数；repository_counts 是导出时该仓库/来源类型的持久总数，
  实体数与版本数独立。elapsed_seconds 截止业务 apply 前，包含采集/源码指纹计算，非完整实验耗时。
  任务内收据核心状态常为 RUNNING，终态后 export 更新快照；公开输出省略凭据、完整目录及异常原文。
- export --scenario 支持 initialization/natural_update/historical_replay/fault_experiment，
  只标注本次导出集合，collection_scenario 保留原始分类，标注本身不执行或证明实验。

G04 真实进程证据在 tests/test_github_entry_processes.py：
两类来源六命令闭环及原核心 CLI 加载 registry；意图后 SIGKILL；真实核心 submit 后/关联前 SIGKILL；
业务 commit 后、导出原子替换前、核心仍 RUNNING 时 SIGKILL；下一 Worker 同 Job 第二尝试成功，
无第二次 HTTP/业务变化；SIGINT/SIGTERM 与重复信号在 HTTP 清理屏障内持续持锁，
清理后才持久 INTERRUPTED。业务 SQLite/HTTP 总超时、输入冲突、查询失败、原子替换故障、
导出重复取消和来源失败隔离的其余证据在 tests/test_github_tasks.py。
这些都是受控 API 的 G04 证据，不能当作 G05 真实远端或对照结果。

1. **七来源真实基线及重复刷新。** 使用默认配置中的两个技能项目、四个普通项目和
   openai/codex Issue 来源，经正式 submit/Worker 建立基线并再用新 UUID 刷新。
   核对仓库远端 ID、默认分支/固定 SHA、Commit 窗口、Release 身份及已保存内容、
   普通 SKILL.md 清单与 blob SHA、Issue 全字段/PR 排除/筛选/UTC 上界/增量分页。
   基线注明 20 Commit、10 Release 内容、100 匹配 Issue 的有限边界；无自然变化也是可验证结果。
   失败或预算耗尽不推进检查点，不通过提高预算掩盖不完整分页；如须预算调整记录理由与配置指纹。
   完成条件：七来源各自真实成功、重复刷新、业务与远端字段核对及终态收据证据齐全。
2. **两技能来源固定真实历史重放。** 每个来源选定真实前后 SHA，保存选择依据、实际远端
   Commit/tree 身份、完整普通 SKILL.md 清单及差分。用既有公开业务 collect/GitHubHTTP
   接口和隔离数据库编排，必要新增仅验收专用脚本，不改变生产 RefreshInput 的默认分支契约。
   不用 mock、合成历史或场景标签替代真实树证据；即使观察到自然更新也要完成固定历史重放。
   完成条件：两个来源都可按固定 SHA 重现新增/修改/删除及明确无变化路径，固定链接可核对，
   symlink/submodule 与完整性边界如实记录。公开 Issue 不为验收而修改。
3. **正常/故障 direct 对照，各三次。** TaskForge 与 direct 使用相同业务代码、固定本地输入、
   相同请求门控/预算和隔离状态目录；每组正常、故障各至少三次，保存双方原始数据。
   先固定实验步骤、故障阶段和等价恢复方式，用事件/屏障或明确持久阶段控制故障。
   故障进程在 finally 终止并等待回收；采集/恢复完成后的业务结果必须先核验再比较耗时。
   记录总耗时、采集耗时、排队等待、恢复尝试、实际请求数及人工操作。
   完成条件：三次正常及三次故障成对可复现，结果/恢复成本可比，不预设框架更快。
4. **正式交接。** 从数据库导出终态公开收据与索引，初始化、自然更新、历史重放、故障实验
   分开保存。建立最终复现文档（建议 docs/github-scenarios.md）和量化证据
   （建议 docs/verification-g05.json），公开内容排除凭据、个人目录和不必要个人数据。
   每项结论链接到真实来源/固定 SHA 与原始收据，记录未覆盖能力及平台限制。
   完成条件：文档命令与当前代码一致，可重现上述三组验收，任何未验收项明确列出。
