## 2. 已验收接口及 G04 必须保持的契约

完整字段、筛选、变化及覆盖说明以 README 和源码为准；以下是入口编排关键约束。

### 输入、执行与采集

- RefreshInput 保存 refresh_id、规范化 state_directory、source、source_generation、operation。
  来源配置和持久输入拒绝未知字段；凭据不进入输入、数据库、日志或收据。
- 默认策略为 2 次额外重试、5/60 秒退避、300 秒单次超时；配置定义见 config.DEFAULT_POLICY。
- project.ExecutionIdentity(execution_id, attempt_number) 为严格非敏感身份。
  refresh_project 与 issues.refresh_issues 接收 data、credential、execution 及可选 transport/trust_env，
  返回 True 表示提交，False 表示相同完整输入已完成。调用方先初始化并登记来源。
- collect_project/collect_issues 只构造完整 BatchWrite，调用方须持来源锁。
  refresh 入口当前自行持锁到 HTTP 客户端及业务提交清理完成；G04 导出也须位于来源锁内。
  如需细化编排接口，保持原有 direct 复用、幂等和取消行为，避免重复取得同一来源锁而死锁。
- 同源锁覆盖完成核对、最新检查点读取、全部网络、业务提交及收据生成。
  HTTP/数据库/凭据子进程在重复取消时等实际清理结束后才释放锁。
- GitHubHTTP 共用一次 AttemptBudget；API 固定 2026-03-10、每页 100、最多 10 页、
  100 次实际请求、累计冷却等待 30 秒、单请求总等待 30 秒。HTTP 不自动重试；
  304 仍核对后页，完整分页须穷尽 iter_pages。生产 trust_env=True，测试 False。

### 检查点与业务状态

- BusinessStore.initialize() 显式建立 business.sqlite/schema v1；核心任务库独立初始化。
  register_source 返回 SourceState；rebaseline 在入口建立新代次，采集重试不重置或创建代次。
  来源换仓库、类型或筛选须显式 rebaseline；预算调整保留基线。
- completed_input(data) 核对完整输入和完成标记；相同输入 True，冲突 StateError。
  已完成旧代次可确认成功；未完成旧代次拒绝网络及检查点覆盖。历史保留。
- apply(BatchWrite) 同事务保存实体、版本、变化、覆盖、检查点和完成标记；complete=False 拒绝。
  False 表示批次已完成；CommitUncertainError 表示独立核对也失败，不能直接重做。
  record_attempt 保存非敏感尝试诊断；save_intent、associate_job 供提交关联使用。
- 项目检查点为 repository_id/repository/default_branch/sha。固定 SHA 的 Commit、
  完整 Release 身份核对及技能树共同通过后才提交；历史异常要求 rebaseline。
  初始 Commit 最多 20、Release 内容最多 10；技能仅普通 SKILL.md，不展开 symlink/submodule。
  Release 编辑核对已存内容及后续新增记录，窗口外旧身份不监测内容。
- Issue 检查点为 repository_id/repository/upper_bound，无项目 SHA。每次请求前固定 UTC U；
  初始最多 100 个匹配的真实 Issue，排除 pull_request，mode=finite_initial_window，
  full_history=false；list_exhausted 记录实际结束情况，有限基线 complete 不代表完整历史。
- Issue 增量 since 为最新成功上界减 60 秒，UTC 秒格式向下取整；固定 state=all、
  sort=updated、direction=desc，必须完成所有分页。只保存 updated_at ≤ U，检查点推进到 U。
  失败、预算中断及仓库 ID 更换均保留旧检查点。
- Issue 保存 id/number/title/body/state/labels/comments/created_at/updated_at/closed_at/html_url。
  body/closed_at 必需但可空；时间规范化 UTC 微秒并核对顺序，标签名称排序去重；
  标题/正文保留原文与 null，规范 JSON SHA-256 为指纹，远端扩展字段忽略。
- labels 全部命中、keywords 在标题或正文任一字段任一命中、numbers 任一命中；
  维度间 AND，空维度不限；标签/关键词 casefold，关键词为字面子串。
  tracked_issue_ids 按来源代次读取关注身份；退出筛选仍持续关注。
- Issue 变化为 initial、added、first_observed_history、closed、reopened、updated、exited_filter。
  初始全部 initial；首次关注且创建时间晚于前次 U 才 added，等于或早于则历史首次发现。
  旧时间不覆盖且不产生变化，同时间内容变化按较晚观察保存；退出可与关闭/内容更新同时记录。
  只保存观察到的状态及评论数，不还原中间事件或完整评论变化。
- 批次覆盖包含前检查点、执行身份、观察 UTC、实际请求数及分层完整性/边界/诊断。
  Issue 覆盖另有 since/U、筛选快照、分页、PR 排除、上界延后与旧快照计数。

## 4. 实现 TaskForge 注册、业务命令和恢复

1. 注册 integrations.github.tasks:registry 的单个 github.refresh 任务，使用 RefreshInput 和既有默认策略。
   任务返回 None，从 get_execution_context() 获取 Job ID/尝试号，按来源类型调用同一采集逻辑。
   正常失败交给现有 TASK_ERROR 有限重试；完成批次重试核对完整输入并重建导出，不重复采集或变化。
2. 提供 python -m integrations.github 的 init/submit/reconcile/show/export/direct 六个命令。
   init 显式初始化核心与业务库、登记配置。submit 指定来源或全部来源，输出 source/refresh_id/Job ID；
   支持显式 --rebaseline 建立新代次，区别于核心人工重放。提交前无可用凭据则失败。
   direct 使用独立执行身份复用采集、门控、来源锁和导出，供 G05 隔离对照。
3. 提交前生成稳定 refresh_id 并先保存非敏感意图，再调用公开 TaskForge.submit 并 associate_job。
   同意图重复命令须核对已有关联，避免盲目创建第二个 Job；不同 refresh_id 不应被误合并。
   submit 结果不确定或关联中断后，通过 reconcile 的公开 get/list 按 Job ID 或 refresh_id 核对。
   核对完整输入；无法确认时保持待核对，不能因查询失败再次 submit。恢复不得直接读取核心私有表。
4. show 展示来源代次/检查点、批次覆盖/变化/诊断及核心 Job/Attempt；失败与未知身份明确返回。
   仅从业务公开读取接口与核心公开查询组合结果，保持实体数和内容版本数独立。
5. export 从业务库重建 JSON 收据和最小 Markdown 索引，以临时文件加原子替换写入。
   保存 UTC、源码版本/指纹、配置指纹、场景、批次与 Job/Attempt、前后检查点、请求数、
   变化/实体/版本计数、耗时和核验结论；区分初始化、自然更新、历史重放、故障实验。
   无 Git Commit 的工作区也有可追溯源码指纹。公开输出排除凭据和个人完整目录路径。
   导出失败保留已提交业务数据；重试或 export 修复，重复重建不改变业务变化。
6. 保持同来源串行、不同来源失败隔离、数据库短事务及 HTTP 生命周期；
   确认业务提交后而核心 SUCCESS 前退出可由同 Job 的重试完成核对与导出恢复。

完成条件：通过真实临时 SQLite、真实核心 Worker/CLI 子进程与受控 API 证明入口闭环，
提交核对、批次幂等、原子导出及故障恢复正确；文件存在或 mock 核心调用不能替代这些证据。
