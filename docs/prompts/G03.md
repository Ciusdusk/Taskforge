## 2. 已有实际接口与覆盖契约

配置与存储接口详见 README 的 GitHub 部分及源码；以下是跨任务关键约束：

- RefreshInput 包含 refresh_id、规范化 state_directory、source、source_generation、operation。
  IssueFilter 有 labels、keywords、numbers；Source(kind="issues") 禁止 scan_skills。
  默认策略为 2 次额外重试，5/60 秒退避，300 秒单次超时。
- GitHubHTTP(store, credential, AttemptBudget(source.budgets), ...) 管理异步客户端。
  get 返回 CachedResponse(etag, body, link)；paginate 返回完整列表。
  iter_pages 保留各页响应元数据，**必须穷尽迭代器**才能证明完整；提前停止不代表完整覆盖。
  默认每页 100、最多 10 页、100 次实际请求、累计冷却等待 30 秒；单次总等待 30 秒。
  每次尝试只使用一个预算；304 仍核对后页，HTTP 不自行重试。
- InstanceLocks(directory).source(source_id) 覆盖完成核对、检查点读取、全部网络及业务提交。
  HTTP 上下文嵌套在来源锁内；重复取消仍等实际 HTTP、客户端与数据库清理后才释放锁。
- BusinessStore(directory).initialize() 显式建立 business.sqlite/schema v1。
  register_source(source, rebaseline=False) 返回 SourceState；rebaseline 在入口创建新代次，
  **采集重试不创建或重置代次**。source_state 读当前或指定历史代次。
  completed_input(data) 先核对完整输入与完成标记：相同输入 True，冲突 StateError；
  已完成旧代次可以直接确认成功，未完成旧代次不能采集或覆盖当前检查点。
- entities(repository_id, "issue") 返回当前 Entity 元组。Entity.updated_at 已规范化 UTC；
  apply 对较旧 updated_at 拒绝实体覆盖，但 **不会自动删除对应 Change**。
  Issue 收集器须先判断旧快照并省略它的变化记录，不能只依赖存储层防止伪事件。
- BatchWrite(input, checkpoint, coverage, complete=True, entities, changes, ...) 通过 apply 一次
  同事务保存业务记录、版本、变化、检查点及完成标记。False 表示相同批次已完成；
  complete=False 拒绝。CommitUncertainError 表示独立核对也失败，不能直接重做。
- record_attempt(refresh_id, execution_id, number, diagnostic=None) 保存非敏感诊断；
  save_intent、associate_job 供 G04 使用，本任务不编排核心 submit/reconcile。
- project.ExecutionIdentity(execution_id, attempt_number) 为严格、非敏感执行身份。
  refresh_project(data, credential, execution, *, transport=None, trust_env=True) -> bool
  是已验收的项目采集入口：调用方先初始化并登记来源，完成重试不发网络。
  collect_project 只构造完整 BatchWrite，要求调用方持来源锁；三部分共同通过后才 apply。
  项目检查点为 repository_id、repository、default_branch、sha。
- G02 Commit 初次最多 20 条，全标 initial；之后固定 SHA 的 Compare 逐页核对元数据与数量，
  分叉、回退、不可比较、超上限保留检查点并抛 RebaselineRequired。
  Release 每次完整身份分页，初次仅存最近 10 条内容，之后存新 ID 并持续核对已存内容；
  初始窗口外旧 ID 不监测编辑。消失保留历史，覆盖中诊断；内容不依赖 updated_at。
  “首次观察到”另统计其中发布时间位于观察时刻前 7 天的数量，不将发现旧发布计为近期发布。
- skills.collect_skills 获取固定 commit 对应原生树；截断时丢弃部分清单并逐子树补齐。
  symlink/submodule 不展开；只有完整清单可判断删除，重命名为删除加新增。
  技能变化身份为 repository_id、before_sha、after_sha、path；固定提交链接保存在 coverage。
- remote.parse 对远端选定字段作严格校验，忽略 API 无关扩展字段；错误不保留远端载荷异常链。
  配置及持久输入继续拒绝未知字段。复用它或同样非敏感的验证方式。

项目覆盖包括前检查点、执行身份、观察 UTC、实际请求数、固定目标，以及 Commit/Release/skills
各自完整性与边界。G03 保留这个分层约定，Issue 不使用项目 SHA 检查点。

## 4. 实现 Issue 完整采集

收集逻辑独立于 TaskForge 包装，接收明确输入、凭据与执行身份，供 G04 direct 复用。
持来源锁后核对完成输入、当前代次与最新检查点；已完成批次不重新应用变化。
网络在事务外。读取并核对远端 repository_id，路径重定向后身份变化要求显式 rebaseline。

1. 初次查询仓库 Issues 列表，固定 state=all、sort=updated、direction=desc；以 pull_request
   字段排除 PR。选择最近更新最多 100 条匹配真实 Issue，标为有限 initial 基线。
   不足 100 条且到末尾也可成功；记录实际覆盖，不能声称全历史完整。
2. 每次尝试在请求开始前记录 UTC 上界 U。增量 since 为上次成功检查点减 60 秒，保持
   查询参数不变并完成所有分页；只应用 updated_at ≤ U，晚于 U 留给后续批次。
   检查点推进到 U，不用列表中最大 updated_at；失败或预算中断保留原检查点。
3. 筛选在本地执行：labels 全部命中；keywords 在标题/正文任一命中；numbers 任一命中。
   维度间 AND，空维度不限。已关注对象退出筛选仍更新并记录退出范围，避免移除标签后失联。
4. 保存接入计划要求的完整 Issue 内容、远端身份、updated_at 和规范化指纹：编号、标题、
   正文、state、标签、评论数、创建/更新时间、closed_at 与原文链接；明确可空字段及规范化规则。
   较旧 updated_at 不覆盖或产生变化；相同时间内容变化按较晚观察保存。
5. 比较已关注前后快照，记录关闭、重开、其他内容更新和退出筛选。
   首次发现的旧 Issue 标“历史对象首次发现”，区分自然新建与初始化；
   只保存观察到的状态，不还原两次轮询之间所有事件，不宣称完整评论变化。
6. 完整增量覆盖通过后构造同一 BatchWrite 原子提交记录、版本、变化、覆盖和检查点。
   同 refresh_id 重试读取最新成功检查点；代次隔离、预算共用与历史保留沿用 G01/G02。

完成条件：真实临时 SQLite 与受控 API 证明有限初始覆盖、完整增量、不误计新增或状态变化、
原子检查点、重试幂等及身份/代次隔离；分页 200 或 BatchWrite 构造成功不能替代这些证据。
