## Obsidian 备份链路

### 任务边界

首版由备份入口生成并记录一个确定的本地 Git commit，再提交 TaskForge 推送任务。
任务参数包括仓库身份、远程与目标分支、稳定 commit SHA 和备份批次身份。
重试始终推送既有 commit，不在每次尝试中重新暂存和提交当前工作树。
TaskForge 的直接贡献是推送任务的持久状态、有限重试、尝试历史和恢复；
Git 提供提交历史、对象存储和传输，两者的收益分别陈述。

### 本地提交与持久关联

- 备份入口在业务状态中先登记批次；生成的 commit 携带可核对的批次身份，完成后记录 SHA。
  入口在 commit 完成但 SHA 尚未登记时退出，下次必须能根据该身份找到既有 commit。
- 没有内容变化时不制造空提交；已有未推送快照仍可进入推送流程。
- 尊重已有暂存内容。遇到用户已暂存改动、merge/rebase 或已有 Git 写锁时停止本次备份并说明原因。
- 同一仓库的自动备份入口与推送操作使用业务层互斥；Worker 并发槽位不能代替仓库互斥。
  其他 Git 客户端不受该业务锁控制，实施验收期间避免同时修改仓库。
- 一个 commit 固定的是 Git index 中的内容；暂存期间发生的新编辑留给下一批次。
  不承诺正在编辑的整个 vault 在同一时刻被原子快照。
- 业务批次关联到 TaskForge Job。两份数据库不能原子提交，需核对待提交批次、
  已提交任务和提交结果不确定的情况；不盲目再次提交，也不声称核心支持业务去重。

### 推送与恢复

- 确认本地对象存在并核对远程分支。远程已经包含目标 commit 时，本次推送视为已完成。
- 远程是目标 commit 的祖先时，执行正常 fast-forward 推送。
- 旧任务重试时，若远程已包含更晚的后继 commit，应确认旧目标已包含，不能回退远程分支。
- 分支分叉、认证失败或远程拒绝应保存诊断。首版使用现有有限重试预算；
  核心尚无按业务异常动态决定是否重试的接口，不宣称永久错误能够立即跳过重试。
- 不自动 force push、重写历史或清理工作树。
- Git 子进程的超时与取消由适配层处理，等待子进程实际结束并回收后才结束任务。
  TaskForge 的协作取消不会自动停止外部子进程。

### 验收

先在独立测试 vault 和本地 bare remote 中验证提交、推送、修改、重命名、删除及无变化批次。
再在真实 PRTS 仓库执行已检查跟踪范围的备份，核对远程确实包含目标提交。
恢复到独立目录，以该 commit 的文件清单和内容哈希验证；不覆盖实际 vault。
保留网络失败、Worker 重启、远程已接受但 SUCCESS 未提交、旧任务晚于新任务执行的证据。
个人笔记内容不进入公共量化收据，只保留必要计数、哈希和匿名化执行信息。

## GitHub 关注链路

### 任务边界与检查点

- 每个配置采集来源一次刷新为一个 TaskForge Job，六个项目来源和一个 Codex Issue 来源
  独立失败、重试和完成；同一来源的刷新串行处理，避免旧批次覆盖新检查点。
- 项目来源读取仓库元数据后固定默认分支的目标 commit SHA；提交历史与技能树都以该 SHA 为准。
- 项目来源初次采集记录基线、技能定义清单和有限历史记录，不把现存全部内容标记为新更新。
  建议初次最多 20 条提交、10 条 Release；这是明确的业务窗口，不是全历史归档。
- 后续采集保存前次成功 SHA 和本次目标 SHA。普通演进按提交差异采集；
  改写历史或差异过大时标记需要重新建立基线，不伪造完整变化记录。
- 超出首版窗口必须标记覆盖范围或未完成状态，不静默跳过记录并推进完整检查点。
- 最终业务记录与检查点在同一业务事务中保存。采集中途失败不推进检查点；
  业务提交完成但核心 SUCCESS 尚未提交时，重试核对已保存结果。
- 提交按仓库和 SHA 唯一识别；Release 按仓库和远端 ID 识别，并能保存内容更新。
  技能变化按仓库、前后快照 SHA、路径识别。再次 submit 的新 Job 也不得产生重复业务记录。

### 技能定义变化

在固定 SHA 上读取完整树，保存 SKILL.md 路径与 blob SHA。
比较前后完整清单以判断新增、修改、删除；重命名首版可表示为旧路径删除、新路径新增。
GitHub Compare API 的变化文件列表上限为 300，不能用它证明完整的技能清单；
Tree API 出现 truncated 时必须补齐子树或明确失败，不得把缺失路径判断为删除。
首版产物是结构化变化记录和原文链接，不要求下载或执行技能代码。

### Codex Issue 关注

采集 [openai/codex Issues](https://github.com/openai/codex/issues)，首版关注新 Issue 和已有
Issue 的更新、关闭、重开。默认不筛选标签；可配置标签、关键词或具体 Issue 编号。
筛选参数变更后重新建立对应采集基线，不能沿用旧筛选条件的完整性结论。

- 首次采集最近更新的最多 100 条真实 Issue，建立有限基线，注明覆盖范围。
  不将这批既有记录计为本周新增，不承诺覆盖仓库全部历史 Issue。
- 保存远端 ID、编号、标题、正文、状态、标签、原文链接、创建与更新时间、关闭时间及评论数量。
  首版不下载完整评论线程，也不据此宣称识别了所有评论变化。
- 使用 GitHub 仓库 Issues API；响应可能混入 PR，依据 pull_request 字段排除。
  查询包含 open 与 closed，避免已关注 Issue 关闭后从采集中消失。
- 后续按更新时间增量采集。以上轮成功检查点为起点，保留 60 秒重叠窗口；
  每批记录请求开始时间作为上界，晚于上界的更新留给下一批。
  完整分页完成后，Issue 记录与本批上界检查点在同一业务事务中提交。
  不使用返回记录的最大更新时间直接推进检查点。
- 分页中途失败或达到单批预算时保留旧检查点，明确未完成；重试按远端身份更新现有记录。
  依据更新时间防止旧快照覆盖新内容，重复提交不产生重复 Issue。
- 验收覆盖 PR 排除、分页、相同更新时间、重叠窗口、关闭与重开、分页中断后恢复，
  并对照真实 API 返回的 Issue 编号、状态及更新时间。关闭与重开可用受控替身验证，
  不为验收修改公开仓库的 Issue。

这项需求体现可变业务对象的增量同步与持久检查点，补充固定 commit 和技能文件快照的接入场景。

### 请求与限流

使用官方 GitHub REST API，处理分页、请求超时和限流。
认证信息仅从本地环境或既有凭据方式读取，不写入任务参数、日志和收据。
优先条件请求，并控制同一认证身份的请求并发；不把 TaskForge 槽位数直接当作 API 并发数。
收到 Retry-After 或明确的限流重置时间时，业务层持久记录最早可请求时间，跨 Job 与重启遵守。
现有核心退避不能动态适配服务端等待时间；若等待超过单次超时预算，明确失败并给出稍后
重新提交的诊断。不能在仍被限流时反复实际请求，也不为一周项目扩展核心调度器。

### 产物与验收

业务存储和 JSON 收据是主要产物；可重建的最小 Markdown 索引仅用于人工核验。
首版输出留在业务目录，报告写入 vault 的联动可随后单独接入。

六个项目来源与 Codex Issue 来源均成功建立各自基线；重复刷新不新增重复记录。
在上游有变化时采集新记录；若准备期没有合适的新变化，可固定真实历史中的两个 SHA
重放技能变化检测。历史重放和本周自然更新必须分别统计。
一个来源失败时其他来源仍可完成；中途退出、业务提交后退出和重启后的结果可核对。
用本地受控替身测试限流、分页、截断和错误响应，同时保留真实 API 兼容性验收。

## 量化与证据

所有数字由实际运行产生，计划中的范围和历史本地计数不作为成果。

| 维度 | 记录内容 | 解释边界 |
| --- | --- | --- |
| 真实备份规模 | commit 文件数、内容字节数、批次数、目标 SHA、远程包含关系 | Git 对象占用不等于文件大小或网络传输流量 |
| 备份完整性 | 独立恢复目录的文件清单与内容哈希一致率 | 恢复测试目录与实际 vault 分开 |
| 真实 API 接入 | 七仓库对应来源的成功覆盖数、有效提交与 Release 数、技能定义数、Issue 数与更新数、请求数 | 初始化、历史重放和自然更新分别统计 |
| 可靠性 | 各故障类型的注入次数、恢复次数、耗时、尝试历史、人工操作次数 | 受控恢复比例不等于长期可用率 |
| 幂等性 | 重复尝试和重复提交次数、重复 commit/记录/报告数 | 幂等来自适配层，框架仍可能重复执行 |
| 执行开销 | 直接执行与框架执行的总耗时、排队等待、业务耗时、资源占用 | 同输入、同并发、同限流条件；不预设框架更快 |

正常业务批次与故障实验分别保存。每条收据至少包含 UTC 时间、源码版本、场景、
业务批次身份、匿名化输入清单、Job ID、尝试号、故障类型、耗时和产物校验结论。
公开收据排除笔记标题、正文、个人完整路径和凭据；对照实验预先固定输入与重复次数。
七个来源不足以外推高吞吐能力，一周记录不足以描述生产长期可用率。

## 实施前仍需核对

- PRTS 的 origin URL 与用户提供地址是否一致、远程 main 是否存在及是否分叉。
- 已有 Git 认证是否可在 WSL 使用；仓库可见性、附件范围和大文件是否符合备份需求。
- 真实恢复目录、业务存储目录、GitHub API 认证方式及可用客户端依赖。
- 备份入口需要处理的 Git hooks 与当前仓库设置；状态检查通过不等于提交与推送已验证。

## 外部契约依据

- [Git commit](https://git-scm.com/docs/git-commit)：提交记录暂存区内容。
- [Git push](https://git-scm.com/docs/git-push)：引用更新与 fast-forward 约束。
- [GitHub 文件限制](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)：按实际附件核对文件限制。
- [GitHub Commits API](https://docs.github.com/en/rest/commits/commits)：固定提交、比较与结果范围。
- [GitHub Trees API](https://docs.github.com/en/rest/git/trees)：树条目与截断处理。
- [GitHub Releases API](https://docs.github.com/en/rest/releases/releases)：Release 查询不包含所有普通 tag。
- [GitHub Issues API](https://docs.github.com/en/rest/issues/issues#list-repository-issues)：更新窗口、状态筛选、分页及 PR 混入处理。
- [GitHub API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)：条件请求、请求并发与限流等待。
